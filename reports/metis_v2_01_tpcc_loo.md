# Metis v2 ① TPC-C・YCSB の固定負荷、評価する状態を除いて学習（2026-11-03）

## 結論

- **go の判定**：3 つの variant すべてが基準（8 状態の TPS/oracle の幾何平均 0.95 以上、どの状態も 0.90 以上）を満たした。
- **主役は v2-A**（probe なし）。手直し後、幾何平均 **1.002**、最小 0.978（W=3）。
- v2-B1 は 0.964、v2-B2 は 0.973。どちらも低 W で N を大きく選びすぎる。
- 制御器には active warehouse 数 W を渡していない。観測するのは、active worker 数・区間の TPS・abort 率だけ。

## 条件

- **TPC-C**：標準ミックス、標準条件（[TPC-C ①](tpcc_01_conditions_and_oracle.md)）。状態は W=1/2/3/4/8/16/32/96。
- **学習**：状態ごとに、N を一様ランダムに選びながら 30 秒 × 2 run（制御周期 200 ms）。
- **評価**：評価する状態を除いた 7 状態の統計量を足し合わせたモデルで、学習を止めて 10 秒 × 2 run（2 run 目は状態の順を逆にした）。
- **oracle**：同じ 8 状態の、固定 N の最高 TPS（10 秒 × 2 run、別の時刻に測定）。比が 1 を少し超えるのは時刻による変動。
- **モデル**：[metis_v2.hh](../include/metis_v2.hh)。実行は [run.py](../experiments/ICDE/metis_v2/run.py) と [pipeline_tpcc_loo.sh](../experiments/ICDE/metis_v2/pipeline_tpcc_loo.sh)。

## v2-A の手直し：予測だけで移る回数に上限を設けた

- **手直し前の問題**：W=3 で、小さい N（8〜14）と大きい N（34〜48）の間を最後まで飛び回った。今いる N で観測する abort 率から予測するので、N=12 から見ると「40 が良い」、N=40 から見ると「12 が良い」と予測が食い違う。直近に測った N を実測値で比べる短期の記憶だけでは、まだ測っていない N へ移り続けるのを止められなかった。
- **規則**：予測だけで「まだ測っていない N」へ移るのは、記憶をリセットしてから最大 5 回まで（`--metis_v2_model_moves=5`）。その後は、実際に測った N の中から最も良いものを選ぶ。
- **上限 3 回との比較**：W=3 で 0.95（96 → 36 → 8 → 48 で探索が終わり、20 付近を試さない）。5 回では 0.98。
- **論文での説明**：モデルが最初の数手で大きく近づき、最後は実測で決める、という役割分担として書ける。

## 追記：YCSB への適用と v2-A の改訂（2026-11-03 夕方）

### 最初の v2-A は YCSB で基準に届かなかった

7 skew（0.7〜0.999）、学習は各 20 秒 × 2 run（制御周期 10 ms）、評価は 10 秒 × 2 run。oracle は [YCSB ②](ycsb_02_oracle.md)。

- 幾何平均 0.913、最小 0.81（skew 0.7）。どの skew でも oracle より小さい N を選んだ。
- 原因 1：physical-first の配置では、YCSB の TPS は socket の境目（N=24）を超えると急に落ちる。thread 数の特徴に socket の境目がなく、この形を表せなかった。
- 原因 2：予測が止まったところでそのまま留まり、最後の微調整がなかった。

### 改訂の内容（[metis_v2.hh](../include/metis_v2.hh)）

| 改訂 | 中身 |
|---|---|
| socket をまたぐ割合を特徴に追加 | φ を 4 次元から 5 次元に。socket 0 の物理コア数（24）を超えた分の割合。CPU トポロジから自動で読む |
| 実測による局所探索 | 予測が止まった後、±4、±2 を実際に試す（最大 4 回） |
| 確定と保持 | 探索が終わったら、実測で最も良かった N に移って固定する。保持中は予測も比較もしない |
| 負荷の変化の検出 | TPS か abort 率のずれが 2 区間続いたときだけ探索をやり直す。YCSB では約 1 秒ごとに 1 区間だけ TPS が 20〜35% 落ちるため |
| 短期の記憶 | 保持時間を 3 秒から 10 秒に |

特徴の次元が変わったので、TPC-C・YCSB とも学習からやり直した。以前の結果は `A_v1_phi4`、途中の版は `fixed_v2a_*`・`fixed_v2b_*` として残してある。

### 改訂後の結果（TPS/oracle、10 秒 × 2 run）

| ベンチマーク | 状態ごとの値 | 幾何平均 | 最小 |
|---|---|--:|--:|
| YCSB | 0.7: 0.99、0.8: 0.99、0.85: 0.97、0.9: 1.00、0.95: 0.98、0.99: 0.98、0.999: 1.00 | **0.986** | 0.974 |
| TPC-C | W1: 0.97、W2: 0.96、W3: 0.97、W4: 0.97、W8: 0.99、W16: 0.93、W32: 0.98、W96: 1.00 | **0.972** | 0.933 |

- YCSB は約 0.3 秒で収束し、その後は保持したまま動かない。ワークショップ版の「数 trial で到達」に相当する。
- TPC-C は収束まで 4〜6 秒かかる。1 回の試行が 0.4 秒（200 ms の安定待ち + 200 ms の測定）なので、10 秒の run では探索の時間が 3〜4% の損になる。
- TPC-C の W=16 は 58 で確定した（最高は 48、0.93）。局所探索が ±4・±2 しか試さないので、48 まで戻れなかった。
- 改訂前の TPC-C の 1.002 は、socket の特徴も局所探索もない版の結果。YCSB を直した改訂で、TPC-C は少し下がった。
